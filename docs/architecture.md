# OmniAgent Architecture Notes

## Current runtime

OmniAgent is a Cordis-free TypeScript runtime built from DSH's core behavior without the DSH plugin runtime. The TUI and Web composition roots explicitly wire the selected model provider, persisted DSH permission snapshot, tools, session store, and audit sink. The built-in file and shell tools enforce the snapshot at execution time, while both frontends consume the same `AgentEvent` stream. Configuration is layered into providers/models, roles, agent profiles, and Markdown agents; `RuntimeResolver` turns a session's agent and model binding into the model client, system prompt, tool allowlist, skill allowlist, capabilities, and context budget for each new turn.

### Configuration, agents, and session selection

`ConfigStore` is a read-through store over `~/.omniagent/config.json`. It opens the final path with `O_NOFOLLOW`, requires a regular file, and caches the raw text plus a SHA-256 revision; unchanged content reuses the parsed snapshot. Invalid JSON or schema fails closed instead of reusing the previous configuration. A running turn keeps the snapshot it started with, so edits apply to the next turn.

`buildConfigCatalog` produces a credential-free view of providers and models. A top-level `model`/`provider`/`reasoningEffort` synthesizes the `default` role; an explicit `roles.default` overrides it. Every other role must reference an existing provider/model, and an optional reasoning effort must be supported by that model. `agentProfiles` maps profile ids to tool and skill allowlists. Model entries carry `contextWindow`, `maxTokens`, `capabilities.imageInput`, and an optional reasoning map: `efforts` converts canonical levels to wire values or `null` to disable reasoning, `budgets` supplies token limits, `default` selects an unspecified level, and `wire` writes dotted paths into the request body. Wire paths reject prototype-pollution segments and the reserved roots `model`, `messages`, `stream`, and `tools`. DeepSeek Messages supplies a default reasoning map; pi-ai routes keep their adapter defaults unless a map is configured. Provider credentials, endpoints, and headers never appear in the catalog, API responses, session events, or logs.

`AgentCatalog` scans `~/.omniagent/agents/*.md` and treats the filename as the agent id. It accepts only regular files (no symlinks), caps files at 512 KiB, validates the id pattern and frontmatter, and resolves `role` and `profile` against the current config catalog. `usage` is `primary`, `subagent`, or `both` (default `both`). Invalid files remain visible as catalog errors but cannot be selected. When `default.md` is absent, a built-in default agent is added; when it is present but invalid, there is no fallback. The frontmatter permits only `name`, `description`, `role`, `usage`, and `profile`; unknown fields are errors and `x-` fields are ignored for future extension. The Markdown body is the agent's system prompt.

Sessions persist two independent choices. `agent/selected` (v1) records the agent id, and `model/selected` (v2) is one of:

```ts
{ version: 2, kind: 'agent' }
{ version: 2, kind: 'role', role: string }
{ version: 2, kind: 'model', provider: string, model: string, reasoningEffort?: ReasoningEffort }
```

`kind: 'agent'` follows the selected agent's role. The final reasoning effort is the binding's explicit effort, then the role's effort, then the model's configured default. Missing selections, unknown agents/roles/models, unsupported efforts, and v1 `model/selected` events are invalid and block a turn; they are never auto-mapped to current defaults. Old sessions are not rewritten or deleted, but they require explicit selection before running.

`RuntimeResolver` is the single composition point used by Web, TUI, and subagents. It refreshes both stores, validates `usage` for root or child sessions, expands the profile's `subagent` group into the collaboration tools, discovers workspace skills and filters them by profile, and composes the system prompt from `config.system`, the agent body, the visible skill catalog, and the subagent-capable agent catalog. It also resolves the model client, reasoning effort, context window, image capability, and a revision hash covering config, agents, selection, tools, skills, and available skill names. Session construction receives the resolved values; it does not parse configuration or agent files itself.

Tool and skill allowlists reduce exposure; they do not grant permissions. `Session` intersects the allowlist with the DSH preset and sandbox policy, so a profile that includes `bash` remains read-only under `read-only`. A model that fabricates a hidden tool call is rejected at preparation time. Skills outside the allowlist are absent from the system prompt and rejected by the `skill` tool. Missing skill names are warnings, not grants. Image input is rejected before the provider request when the selected model has `capabilities.imageInput: false`.

### Durable sessions

Sessions are stored as append-only JSONL files:

```text
~/.omniagent/sessions/<workspace-key>/<agent-id>/session.jsonl
```

The first line is a versioned session header. Later lines are typed events with contiguous `seq` values. Appends are persisted immediately; `flush()` remains available for repair checkpoints. Each append is staged, fsynced, and atomically renamed after identity and metadata checks. Invalid JSON, empty records, or non-contiguous sequences reject the log and preserve the original bytes; a valid final record without a newline can be normalized before a later append. Session identity is checked against both workspace and id. New session directories and files are created with private permissions, but existing files are not automatically changed. Writers of one session are serialized across OmniAgent processes by a sibling `wx` lock that records the holder PID and is taken over only when that process is gone; the existing file is re-read under the lock so an append never overwrites events committed by another process. The lock does not constrain non-cooperating external writers, which are still detected by the pre-rename metadata check. Workspace registry updates remain single-process and can lose concurrent changes. Existing sessions whose stored workspace spelling differs from the canonical registered path are not auto-matched or migrated.

The model history is a projection of current `message/user`, `message/assistant`, and `message/tool-result` events plus the older `user/message`, `assistant/message`, and `tool/result` aliases. The log is the source of truth, not a separately persisted message array. When an interrupted or failed batch is missing tool results, provider input is repaired with a result stating that execution status is unknown; duplicate calls and orphan results are omitted from that input only. The durable log and visible history are not rewritten. When such a repair is necessary, later turns may repeat context compaction because the compacted provider input is not substituted for the raw history.

### Runtime loop

`AgentLoop` keeps the DSH-shaped turn/step lifecycle: provider request, optional stream settlement, assistant message, per-call DSH preparation, tool execution, observation, and continuation. A `Session` captures an immutable `DshPermissionSnapshot` for the turn. Ordinary `workspace-write` calls do not require a prompt; a model-requested wider sandbox is approved once and is never persisted as a reusable grant. `danger-full-access` uses no DSH file sandbox and its approval policy is `never`. Before each provider request the loop can estimate pressure and compact history without splitting an assistant tool call from its result. Web and TUI derive the input budget from `contextWindowTokens` when configured, otherwise from the selected model's catalog context window; sessions without either budget do not auto-compact. The live `context.compacted` event exposes the before/after estimate to UIs.

The built-in `bash` capability is injected by `Session` with a policy rebuilt from the per-turn snapshot. When a resolved agent profile is present, only allowlisted tools are registered and disclosed; `write_file` and `edit_file` are sandbox-wrapped only when allowed, and `bash` is injected only when allowed. The same allowlist is checked again in `prepareToolCall`, so a fabricated call to an unregistered or disallowed tool is rejected. The `write_file`, `edit_file`, and `bash` capabilities alone may request a one-shot wider sandbox. Other registered tools are trusted only in `danger-full-access`; confined presets deny arbitrary extension tools because the Session has no sandbox policy for them. `read_file`, `list_dir`, `glob`, `grep`, `web_fetch`, and `skill` remain trusted read-only capabilities. Before a provider request, history containing image content fails if the selected model does not support image input.

The TUI renderer is presentation-only: it buffers complete Markdown lines for the assistant body, renders `assistant.reasoning.delta` through a dimmed reasoning block, and folds `tool.call`/`tool.result` pairs into one status row with a tool-specific summary and bounded output preview. Reasoning deltas are live-only and are not written to the session transcript. Tool arguments and results are sanitized for terminal control characters before display; verbose mode is an explicit user choice, not persisted in session data. Four block families keep distinct left edges (body at two spaces, reasoning behind `┊`, tool result bodies behind `│`, and notices/summaries behind a glyph), tool rows are colored by outcome with a `○ → ●` pending-to-settled ring, and every normal turn closes with a `✓ 完成` line. `palette.ts` is the single role-to-SGR table; it allows only ANSI 0–15 foregrounds and attributes (no RGB, no backgrounds) so a terminal color scheme remaps the whole UI, `dim` (SGR 2) replaces fixed gray for recessed text, and `roleViolations()` turns that boundary into a test gate. Colors are switchable at runtime with `/color`, and the pending-header ticker exists only while a tool runs. See [ADR-0003](adr/0003-tui-visual-hierarchy.md).

### Todo, plan mode, goals, and subagents

`todo_write` is a model-facing whole-list replacement. Each call appends a `todo/write` event with the complete validated list; duplicate entries are rejected. By default at most one item may be `in_progress`; `config.todo.allowParallelInProgress: true` allows several, which suits work delegated to concurrently running subagents. The standing projection is the latest well-formed write, retained across model steps and retired by the next user message (the start of the next turn). TUI prints the list after each update, and Web includes it in session details and the live conversation footer.

Plan mode is a persisted `plan/mode { active }` session state, exposed through the TUI `/plan` command and the Web plan toggle. While active, the system prompt receives DSH-style planning guidance and `exit_plan_mode` is disclosed. The tool requires a non-empty Markdown plan that starts with a level-one `# ` heading, sends the complete plan to the host review callback, and only clears plan mode after approval; a keep-planning decision is returned to the model as a tool error carrying the user's feedback. Plan mode is guidance and reviewed state, not a sandbox or permission preset: the standing preset still controls writes and command execution.

Goals are persisted with `goal/change` full-snapshot events and compared by `(id, revision)`. `get_goal`, `create_goal`, and `update_goal` expose the current objective, phase (`active`, `paused`, `blocked`, `complete`), admitted round count, round cap, and process-local activation (`armed`, `disarmed`). Creation, editing, pausing, and resuming require a direct human turn on a top-level agent; completion and blocking are also accepted from the exact active goal round. A model-reported blocker requires the concrete condition to persist for at least three goal rounds. An active, armed goal automatically continues after the current turn with a `<goal_round>` user message whose source identifies the goal revision and round; the round count is folded from those messages. The driver stops on completion, blocking, pausing, disarming, turn interruption (which pauses the goal), error, the round cap (which blocks with `round-limit`), or when no armed active goal remains. Terminal autonomous updates inject a wrap-up notice so the model writes one closing message instead of silently stopping.

Subagents are independently persisted sessions with a `parentSessionId`, depth, and description. The `subagent` tool starts one asynchronously and returns its id; `send_message` steers a running child or starts/continues an idle one, `list_agents` returns the root plus every continuable descendant with id/label/status/parent/depth, `wait_agent` waits for input at the caller's next step (messages, completion notices, or steering) for 10 seconds to 1 hour, and `interrupt_agent` can stop a descendant. `list_agents`' `running` only means a turn is executing; `inactive` does not report success or failure. `subagent` accepts an optional `agent` (defaults to the parent's agent), an optional `role`, or an explicit provider/model pair; `role` cannot be combined with provider/model, and `provider`/`model` must appear together. The target agent must allow subagent usage. The resolver builds the child model from the target agent's role unless a binding override is supplied, and the child records both `agent/selected` and v2 `model/selected` events. A child inherits the creator's exact permission preset, workspace containment, and cwd restrictions, and is subject to `maxDepth` and `maxActive`. Completion appends `subagent/end` and wakes a live parent through `receiveSubagentNotice`; if the parent is not live in this process, a `subagent/notice` event is persisted for its next turn. A message queued after the parent's final step triggers a background turn rather than remaining unread. Persisted children can be lazily reopened by `send_message` in a later process only when both selections are valid; otherwise the resume fails closed.

### Security boundaries

The DSH permission layer has three explicit presets: `read-only`, `workspace-write`, and `danger-full-access`. A session stores its choice as a `permission/dsh-preset` event; an empty, legacy, invalid, or unknown event history cannot authorize tools and requires explicit selection. `read_file`, `list_dir`, `glob`, and `grep` apply a physical-path workspace fence in every preset, including symlink-escape rejection; built-in `write_file`/`edit_file` mutations reject hard-linked targets. The shell backend enforces writes through Seatbelt, bubblewrap, or configured Landlock, and workspace-write additionally fails closed when its writable roots contain a pre-existing hard-linked regular file. That preflight does not scan host temp roots, so a pre-existing hard link under `/tmp` or `$TMPDIR` remains a residual write-through path. These controls still have TOCTOU windows, and they constrain file writes and process execution, not network access or all reads; they are not a VM or complete OS security boundary.

### Web workspaces

The local Web host registers its starting directory in `~/.omniagent/workspaces.json`. A workspace is an existing directory identified by a stable ID and its canonical real path. Registering a second spelling of the same path reuses the existing workspace. Unregistering a workspace only removes it from the registry; it does not remove the directory or its saved sessions. A workspace may be registered again later.

Every Web session request includes the workspace ID. The host resolves that ID through the registry and uses the resulting workspace path and session ID together to find or create a session. Session admission projects `agent/selected` and v2 `model/selected` and resolves them through `RuntimeResolver`; a missing or invalid selection returns `409` instead of falling back. Cached `Session` objects are keyed by the workspace/session pair plus the permission preset, serialized model binding, and resolver revision, so a config or agent edit rebuilds the runtime on the next turn. `GET /api/agents` and `GET /api/roles` expose credential-free catalogs, and `GET /api/models` reports capabilities and supported reasoning efforts. `POST .../agent` and `POST .../model` persist switches while no turn is active. Conversation history comes from the session log. Lifecycle, tool, permission and compaction trace events are available in the Observe view; Web audit records are stored under the application configuration directory, filtered by workspace and session, and omit both argument digests and permission rule source text from the API projection. Workspace-local audit files used by older versions or the TUI remain untouched and are not automatically imported. The TUI writes its audit log to `<workspace>/.omniagent/audit.jsonl`; arguments are hashed, a newly created directory is `0700` and a new file is `0600`, while pre-existing directory and file modes are left unchanged. A symlinked or non-regular audit target is rejected instead of followed. Another process running as the same OS user can still read the log. A trace does not duplicate tool arguments or full tool output. Session messages and raw audit logs can contain sensitive content, so both must be treated as private data.

The shell sandbox has the same boundary: it constrains writes and process execution, but a confined process can read any file the current OS user can read and may reach loopback services, including the local Web control plane. The Web host does not authenticate local users; active turns and session creation reject permission/default changes as a race guard, not as a substitute for authentication. Callers that bypass `Session` and its `prepareToolCall` hook do not automatically receive the DSH file/shell policy. Web/TUI composition roots use `Session`.

The trajectory projection derives Input / Model / Tools records from the persisted event order. It does not infer model latency or duplicate sensitive message text, tool arguments, output, or rule sources. Its recorded-time tool intervals represent the observed call-to-result event timestamps; explicitly recorded execution duration is a separate value. The Observe view offers Records and Events lists with filtered metadata details; live stream events appear there only after persisted session details are reloaded. DSH's timeline drag, zoom, and pan interactions are not implemented. The session menu exports a versioned JSON transcript or copies Markdown for one session, not a DSH ZIP archive with descendant logs or attachments. Exported message text and tool output may contain secrets and must be reviewed before sharing.

### Skills

The filesystem catalog discovers project `.agents/skills`, custom roots, and the user skill directory. It supports both `<skill>/SKILL.md` and flat `<skill>.md` files. Catalog entries load frontmatter and a short description; full instructions are read only through the model-facing `skill` tool. Earlier roots win on duplicate names, files above 1 MiB are rejected, and skill discovery is independent of the Cordis/DSH plugin runtime. `RuntimeResolver` filters the discovered catalog by the selected agent's `agentProfiles.skills` allowlist; missing names produce warnings but no grants. Web and TUI inject only the allowed catalog into the session system prompt, and the `skill` tool re-checks the same allowlist on every load, so a skill cannot be loaded by guessing a path or by a fabricated tool call.

### Known limitations

- The file fence resolves physical paths, rejects symlink escapes in `read_file`/`list_dir`/`glob`/`grep` and hard-linked built-in write/edit targets, and still has TOCTOU limitations. Shell hard-link preflight covers workspace and additional writable roots, not host temp roots.
- Confined shell execution has been verified with Seatbelt on macOS and the Landlock fallback on Linux x86-64; Linux bubblewrap and other native architectures still require real-host verification. Windows confined execution and workspace-write file fencing remain unavailable and fail closed. The upstream DSH Windows ACL backend persistently changes workspace ACLs and integrity labels and has hard-link limitations, so it is not silently enabled here.
- Session append uses a cross-process PID lock, fsync, and atomic rename; non-cooperating external writers can still race between metadata validation and rename, and each append copies the existing log.
- Context estimation and compaction use the selected model's catalog context window or explicit config; a model with no catalog window and no configuration does not auto-compact.
- Plan mode is persisted guidance, not enforcement. A model can still write or run commands while plan mode is active if the standing permission preset allows it.
- Tool and skill allowlists reduce exposure only. The DSH preset and sandbox remain the authorization boundary, and loaded skill text is model context, not trusted instructions.
- Configuration and agent files are re-read per turn. Invalid configuration, an invalid agent, an unknown role/profile/model, or an unsupported reasoning effort fails closed; the runtime does not reuse the previous snapshot or choose a different default for that turn.
- Agent selection v1 and model binding v2 are the only accepted session selections. Missing agent events and v1 `model/selected` events are invalid and require explicit reselection; existing sessions are not migrated, rewritten, or deleted.
- Subagent limits are in-process. `maxActive` counts work in one runtime. A child lazily resumed by a new process is resolved from its own persisted agent and v2 model binding; if either selection is missing or invalid, the resume fails closed instead of inheriting the parent's current model. Its persisted messages, permission, model, and workspace are preserved.
- A Web subagent runs as a background session and is not attached to the initiating turn's SSE approval stream. Its normal workspace operations still run under the inherited preset, but a one-shot sandbox escalation is denied because no live approval handler is bound, and child plan review is unavailable. The TUI passes its terminal approval callback to children. Background completion notices are persisted; the Web UI sees them when the parent session is reloaded or when a background turn produces new stored events, not through the original SSE response.

```bash
pnpm test
pnpm typecheck
pnpm dev       # interactive TUI with /sessions and /resume
pnpm web       # local UI at http://127.0.0.1:4317
```

The Web server accepts `OMNIAGENT_PORT` for a different loopback port. Providers and API keys remain outside session files and are read from the existing config/environment mechanism.
