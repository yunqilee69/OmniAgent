# ADR-0003：TUI 用角色调色板 + 三块左缘，而不是引入全屏终端框架

状态：已采纳 · 2026-11

## 背景

TUI 的第一版能跑，但一屏里四类内容读起来是糊的：思考、正文、工具、通知**都从第 3 列开始**，思考正文和工具结果还共用同一条 `│` 竖线；颜色是散落的 `dim+gray`、`cyan`、`magenta`，没有「这段是什么身份」的概念；工具调用是原地闪烁的一行状态再跟一段无边界预览；连正常结束的回合也没有收尾行。结果就是长对话只能逐字读——这正是「混在一起」的具体含义。

参考实现（`../deepseek-harness` 的 TUI 设计笔记）给出一条可迁移的结论：终端里的层次不靠装饰，靠三件事——**固定左缘、单一角色表、可扫读的状态头**。它同时提醒了两个反例：一是 `dim` 用固定灰（SGR 90）在浅色背景上会变成一块更重的颜色；二是按角色名冒充「语义样式」却让组件各自发 SGR，最终没人能验证配色是否越界。

## 候选方案

**A. 引入 Ink / pi-tui 做全屏差分渲染。** 能拿到固定底栏、`Ctrl+O` 折叠、整屏重绘。
- 优点：交互上限最高，也是 DSH 的选择。
- 缺点：它们自带 raw 输入、光标状态、TTY 专用生命周期和 overlay 系统；本项目的 TUI 定位是「每一层都短到能一眼看完」，引入后 `main.ts` 会被替换成一套终端应用框架，与[ADR-0002](0002-core-tui-seam.md) 的分层前提也冲突（事件流是为「换前端」准备的，不是为「同一个前端换渲染引擎」准备的）。

**B. 保留 `readline` 逐行打印，只在渲染层建立层次。**
- 优点：改动集中在 `render.ts` 与新拆出的两个模块；核心协议、会话、权限一律不动；管道/非 TTY 场景天然安全。
- 缺点：拿不到固定底栏与折叠；颜色一旦写出就不能重绘历史行。

**C. 只调颜色，不改左缘。** 最小改动，但「用颜色区分四类内容」在 16 色下区分度不足，且对色觉障碍与 `NO_COLOR` 用户完全失效。

## 决定

采用 **B**，并把「长什么样」从「什么时候画」里拆出来：

1. **`palette.ts` 是角色 → SGR 的唯一事实来源。** 组件不再写 `{ fg: 'magenta' }`，而是取 `roles.reasoning(...)` 这类包装器。只用 ANSI 0–15 前景与属性，禁止 24 位 RGB 与背景色，因此浅色/深色终端都能整体重映射，不另设主题。内收文字一律 `dim`（SGR 2），不用固定灰。`roleViolations()` 把这条约束变成可断言的闸门。
2. **`blocks.ts` 负责块的文本构建**（思考头、工具卡头与体、通知、回合尾行、状态行、帮助），纯函数、可单测，渲染器只决定顺序与间距。
3. **四类内容各有左缘**：正文 `2 空格 + Markdown`、思考 `┊ 虚线导轨 + 内收斜体`、工具结果体 `│ 实线导轨 + 内收`、通知与回合尾行用引导符（`◇`/`⚠`/`✗`/`✓`/`■`）。`Assistant` 标签每回合出现一次，给正文一个「谁在说话」的锚点；正常回合也打印 `✓ 完成 · 8s` 收尾，让下一句提问和上一段回答之间有结构边界。
4. **工具卡 = 一行彩色状态头 + 一块内收体。** 头部整行由结果上色（待定黄 / 成功绿 / 失败红 / 拒绝亮黄），`○ → ●` 表示待定到已定，待定期间原地刷新耗时；失败时体部也转红，避免「只有头部变色、正文看起来正常」。
5. **输入区独立成行。** 状态行（会话 / 权限 / 模型 / 模式 / todo）由渲染器单独打印，`rl.question` 只拿到一行 `❯`——readline 用提示符宽度算光标列，多行 prompt 会让编辑与回显错位，所以状态行**不合并进 prompt**。
6. **等待提示只在没有内容可看时出现**：等首个 token 时是转圈 + 耗时，工具执行时是卡片头部的耗时；正文/思考一开始就清掉。不设常驻底栏。
7. 写入路径上最多保留一个连续空行，块间距只由 `enterBlock` 决定，避免模型正文自带的尾部空行与渲染器补的空行叠加成两三个空行。

## 后果

- 长对话可以凭列位和颜色扫读：思考、回答、工具、通知各自的左缘不同，工具卡是一列颜色一致的状态头。
- 颜色完全可关：`/color off`、`NO_COLOR=1`、`TERM=dumb` 都退回无 ANSI 的纯文本，此时层次仍由左缘与引导符承担——这是把「颜色」当增强而不是当信息载体的收益。
- `dim` 取代 `gray` 后，浅色终端上不再出现「次要文字比正文更重」；`markdown.ts` / `highlight.ts` 里所有 `dim+gray` 组合一并收敛到 `dim`。
- 代价一：`/color` 只影响之后写出的内容，已落到终端的历史行不会重绘（逐行打印的固有限制）。
- 代价二：仍然没有固定底栏、`Ctrl+O` 折叠、整屏重绘；这些要靠候选方案 A，属于将来的独立决定。
- 代价三：工具头文案从 `✓ 读取文件 · README.md · 2 行` 改为 `● 工具 / 读取文件 · README.md · 2 行`，是一次可见的输出变更，测试同步更新。
- `❯` 只在 `renderPrompt` 出现一次，`main.test.ts` 靠它数 prompt 次数；这条「唯一性」从隐式约定变成需要维护的约束。

## 测试

`packages/tui/src/blocks.test.ts` 覆盖角色表完备性、`dim` 与 `dimItalic` 的 SGR、`roleViolations` 对 RGB/256 色/背景色的拒绝、三块导轨互不相同、工具头按状态上色、窄宽度下摘要截断与状态行分段裁剪、`❯` 唯一性与帮助命令表、耗时粒度。

`packages/tui/src/render.test.ts` 覆盖层次保持（思考行含 `┊`、正文行既不含 `┊` 也不含 `│`、块间距不超过一个空行）、工具头随 `ok` 变色且失败体转红、整段输出不越出 16 色角色表、等待提示在内容到达后清行、待定卡片原地刷新为结果行。

`packages/tui/src/main.test.ts` 未改断言，仍靠 `❯ ` 计数与会话事件断言 REPL 行为，确认重构没有改变交互契约。
